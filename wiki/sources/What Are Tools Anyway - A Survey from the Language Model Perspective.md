# What Are Tools Anyway? A Survey from the Language Model Perspective

Zora Zhiruo Wang, Zhoujun Cheng, Hao Zhu, Daniel Fried, and Graham Neubig
(2024).

## Brief

This survey gives “tool” a precise boundary: an **external computer program
exposed through a function interface whose calls and arguments are generated by
the language model**. It organizes tools by what they do, reviews prompting,
training, selection, composition, and tool creation, and argues that evaluations
must measure more than task accuracy. Its most durable contribution is a set of
questions for deciding whether a capability is truly a tool, when tools help,
and what their real costs and risks are.

## Summary

### Definition and functions

The authors distinguish a tool from computation internal to the model. The
implementation can be symbolic or neural, but it runs externally and has a
programmatic interface invoked by model-generated calls. Tools serve three
overlapping functions:

- **Perception:** obtain information from the environment, such as search,
  database access, current time, or weather.
- **Action:** change environment state, such as creating a calendar event,
  sending a message, or controlling a robot.
- **Computation:** transform information without necessarily observing or
  changing the external world, such as calculation or translation.

A search engine can be both perception and computation; SQL can compute, read,
or mutate depending on the query. Under a classical agent definition, a model
using only computation tools is tool-augmented but not necessarily an agent:
agency involves perceiving or acting on an environment.

### Basic and advanced tool use

The basic loop alternates text generation and a serialized function call. A
server executes the call, returns an observation, and generation continues with
that result in context. Models can acquire this behaviour through inference-time
instructions, tool documentation, and demonstrations, or through training on
human-written, teacher-generated, or self-bootstrapped tool trajectories.

Useful scenarios include knowledge access, exact or complex computation,
interaction with digital or physical environments, non-text modalities, and
delegation to specialized models. Tools are less compelling when the base model
already performs the task well and the proposed tool is merely a smaller neural
model with no distinctive information or algorithmic advantage—for example,
some forms of summarization, sentiment analysis, or translation.

As the toolbox grows, selection changes from placing all tool descriptions in
context to retrieving a relevant shortlist. Complex tasks may require sequential,
nested, parallel, or iterative calls. Programmatic settings blur the boundary:
built-in language operations, external libraries, and task-specific utility
functions can all act as tools relative to a chosen base environment. When no
suitable tool exists, models can compose primitives into reusable abstractions
or create, test, retrieve, and reuse new programs.

### Evaluation and efficiency

The survey distinguishes repurposed reasoning datasets from aggregated API
benchmarks. The latter often use model-synthesized tasks that may be unnatural,
combine tools that would not be used together, or cannot execute the advertised
APIs. Five of the nine surveyed API benchmark families do not evaluate actual
execution, forcing tool-call string or syntax matching as a proxy for outcomes.

Existing evaluations emphasize task completion, tool selection, and occasionally
tool reusability. The authors argue for additional measurements: integration
compute, tool latency and resource cost, tool quality, reliability of stochastic
or changing outputs, reproducible testing, and security. For stateful or
time-varying APIs, they suggest executing candidate and reference programs in
parallel rather than comparing against a stale static answer.

Their empirical cost analysis normalizes extra training and inference tokens
and reported performance gains across several papers. It suggests that tools
help most when they provide a genuinely different capability: Toolformer's
calculator yields large math gains, while its translation tool does not improve
the multilingual aggregate. The ranking also changes when one-time training
cost is separated from recurring inference cost. Because the underlying papers,
baselines, tasks, and model sizes differ, these plots are directional—not a
controlled leaderboard.

## Key ideas to keep in mind

- A tool is defined relative to the model boundary: an external executable
  function called by the model, not simply any useful intermediate reasoning.
- Ask whether a tool **extends** the model with unavailable information/action or
  **facilitates** a task using a more reliable computational mechanism.
- More tools create a retrieval and planning problem; listing every schema in
  the prompt does not scale.
- Evaluate actual task outcomes whenever possible. Correct-looking call syntax
  is a weak substitute for executing the tool.
- Tool quality and tool-policy quality are separate variables; an agent can call
  the right unreliable tool or call a reliable tool incorrectly.
- Training cost, per-request tokens, latency, API cost, failure rate, stability,
  reusability, and safety can reverse a conclusion based on accuracy alone.

## Questions and caveats

- The proposed definition deliberately excludes internal model mechanisms, but
  boundaries become ambiguous when an external “tool” is another hosted LM.
- Claims about where tools are not useful reflect the models and specialized
  systems available in 2024 and can change with capability and cost.
- Cross-paper compute estimates depend on reported numbers and simplified FLOP
  assumptions; some methods could not be measured.
- Synthetic API benchmarks can exaggerate the need for tools by designing tasks
  around designated APIs and depriving the baseline of required information.
- The survey identifies security as missing from evaluation but does not provide
  a comprehensive threat model or safety framework.
