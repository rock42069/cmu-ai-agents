# Toolformer: Language Models Can Teach Themselves to Use Tools

Timo Schick, Jane Dwivedi-Yu, Roberto Dessì, Roberta Raileanu, Maria Lomeli,
Luke Zettlemoyer, Nicola Cancedda, and Thomas Scialom (2023).

## Brief

Toolformer is a method for teaching a language model to decide **whether, when,
and how to call external tools** without a large human-labelled tool-use
dataset. Starting from only a few demonstrations per API, the model proposes
calls within ordinary text; the calls are executed and kept only when their
results make the following tokens easier for the model to predict. Fine-tuning
on this automatically constructed corpus turns API use into part of language
modelling itself. The central contribution is therefore not a new runtime agent
loop, but a self-supervised way to create tool-use training data.

## Summary

### Motivation

Scaling language models does not directly solve limitations such as exact
arithmetic, access to current or rare facts, low-resource translation, and
awareness of the current date. External tools can cover these weaknesses, but
earlier approaches generally needed extensive supervision or task-specific
examples that specified which tool to use.

Toolformer instead asks whether a pretrained model can bootstrap its own
general-purpose API-use examples while retaining its ordinary language ability.
The experiments use five text-in/text-out tools: a retrieval-augmented question
answering model, Wikipedia search, a four-operation calculator, machine
translation into English, and a calendar returning the current date.

### Method: sample, execute, filter, fine-tune

For each API, a small prompt containing demonstrations teaches the base model
the textual syntax of a call. The model then annotates a large language-modelling
corpus by proposing candidate call positions and arguments.

The system executes every candidate. For a call inserted at position `i`, it
compares the weighted loss on subsequent tokens when the model sees the call
and its result against the better of two baselines: seeing no call, or seeing
the call without its result. A call survives only if the returned information
reduces future-token loss by at least a threshold. The retained calls from all
tools are inserted into the original text, and the model is fine-tuned with the
ordinary next-token objective.

This filter is the key idea: **usefulness is defined from the model's own
predictive perspective**, rather than by a human label saying that a call looks
appropriate. At inference time, generation pauses when the model emits the API
result marker, the external tool is executed, its response is inserted, and
generation resumes.

### Experimental findings

The main Toolformer model is based on GPT-J with 6.7B parameters. In zero-shot
experiments, access to tools substantially improves results on factual cloze,
math word problems, question answering, multilingual QA, and temporal tasks.
Examples include large gains over both ordinary GPT-J and a Toolformer variant
with calls disabled: on the three math benchmarks, Toolformer scores 40.4,
29.4, and 44.0 versus 14.8, 6.3, and 15.0 when disabled. It also exceeds the
reported OPT-66B and GPT-3-175B baselines on those benchmarks.

The pattern is not uniformly positive. Wikipedia search improves the GPT-J
baseline on QA, but Toolformer still trails GPT-3. Translation calls help on
each MLQA language, yet fine-tuning on the chosen CCNet distribution harms some
languages enough that the final model does not consistently beat vanilla GPT-J.
On TempLAMA, gains mostly come from QA and search—not the calendar—because the
one-call restriction prevents obtaining the date and then using it in another
query. The separate date benchmark does benefit from the calendar.

Fine-tuning with the augmented corpus does not worsen perplexity relative to
fine-tuning on the same corpus without calls when calls are disabled. Scaling
experiments also show that merely exposing a model to tools is insufficient:
useful tool behaviour emerges around 775M parameters in this setup, with the
smallest tested models gaining little.

### What the results actually establish

The experiments support the claim that useful tool-call supervision can be
bootstrapped from a language model's predictions and a next-token-loss filter.
They do not establish a general autonomous agent capable of long-horizon,
multi-tool work. Evaluation permits at most one API call per input, and decoding
promotes an API call whenever its start token is among the top `k` candidates
(`k = 10` in the main experiments). That intervention makes calls much more
frequent and can reduce the model's natural calibration about when a tool is
needed.

## Key ideas to keep in mind

- Tool-use data can be generated by the model itself, provided there is a
  measurable test for whether a tool result was useful.
- The important supervision signal is **counterfactual improvement**: did the
  returned result help predict what came next compared with no useful result?
- A uniform textual API representation lets ordinary next-token training absorb
  heterogeneous tools without changing the vocabulary or objective.
- Tool choice has at least four separate problems: deciding **whether** to call,
  choosing **which** tool, producing valid arguments, and incorporating the
  result. Toolformer attempts to learn all four from the augmented corpus.
- Tools complement model capacity; they do not remove the need for a capable
  base model.
- Benchmark gains should be read alongside the decoding policy and evaluation
  constraints, especially the top-`k` call trigger and lenient answer metrics.

## Questions and caveats

- Calls are generated independently, so the method cannot learn to feed one
  tool's result into another tool or iteratively refine a failed search.
- The future-token-loss filter measures predictive usefulness, which is not the
  same as factual correctness, task success, safety, or value relative to cost.
- Some tools yield very few retained examples even after processing more than a
  million documents; the paper identifies substantial sample inefficiency.
- Tool selection is sensitive to prompt wording, and the method does not model
  tool-specific latency or computational cost.
- Several evaluation metrics are deliberately lenient for zero-shot generation,
  and some baselines use models or tool systems with different capabilities.
- The released paper evaluates a particular 2023 model and tool set; its
  numerical results are evidence for the mechanism, not timeless estimates of
  modern tool-using systems.
